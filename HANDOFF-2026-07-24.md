## 4. 🎯 Decisión de arquitectura: local + túnel (NO Vercel Preview)

Se **descartó** usar Vercel Preview deployments como ambiente dev. Se trabaja en **local con `npx shopify app dev` + túnel Cloudflare** contra la dev store.

**Por qué:**
- Vercel **Hobby** sí tiene previews, pero: timeout de función de **60 s**, retención de 30 días y configuración extra de OAuth por cada URL de preview.
- El ciclo local es mucho más rápido para el 95% del trabajo (hot reload, sin deploy por cada cambio).
- `automatically_update_urls_on_dev = true` en `shopify.app.dev.toml` hace que el CLI reescriba las URLs de la app **Dev** automáticamente con la del túnel. **No afecta a prod** porque la config activa es la de dev.

Preview solo se consideraría si algún día hay que probar comportamiento serverless real (timeouts, cron).

> ⚠️ Aviso aparte, fuera de alcance pero a vigilar: **producción corre en Vercel Hobby**, que es de uso no comercial y cuyo techo de 60 s ya roza la creación de las 541 variantes de Greta. A futuro, evaluar **Vercel Pro** (resuelve timeout + ToS).

## 7. Cómo pasar dev → prod (referencia, aún no se usa)

- **Código:** PR `dev` → `main`; el merge dispara el deploy Production en Vercel (el build corre `prisma migrate deploy`).
- **Si cambió el toml** (scopes/webhooks/extensiones): `shopify app config use shopify.app.toml` → `shopify app deploy` → **volver a `dev` inmediatamente**.
- **Migraciones:** siempre **expand/contract** (aditivas/nullable, nunca DROP en caliente). `npx prisma migrate dev --name X` en dev, commitear el SQL, Vercel lo aplica a prod.
- **Rollback en 2 niveles:** (1) feature flag OFF (segundos, sin deploy); (2) Vercel Instant Rollback (revierte código — seguro solo si la migración fue aditiva). Nunca rollback destructivo de migración: **forward-fix**.
- **Checklist pre-deploy:** probado en dev store · typecheck + lint OK · migración aditiva y commiteada · feature detrás de flag apagado · diff revisado (¿afecta a Greta/NYZA/Vermú fuera del flag?) · env vars de Production correctas · tras el deploy, verificar que las campañas activas siguen intactas.

## 9. Entregable de análisis — feature "Descuento Incremental por unidad"

**Qué pidió el cliente potencial:** que cada unidad adicional del mismo producto tenga MAYOR descuento (1ª unidad 10%, 2ª 15%, 3ª 20%, con tope opcional). NO es volumen tradicional (todas al mismo %), ni BxGy, ni porcentaje simple.

- ✅ **Es posible en Shopify**, pero **NO con la arquitectura actual** de DiscountFlow.
- ❌ **El enfoque actual (editar el precio de la variante vía `productVariantsBulkUpdate`) es incompatible:** una variante tiene UN solo precio; no puede haber precio distinto por unidad en el mismo carrito.
- ✅ **Única vía nativa = Shopify Functions (Discount Function API).** La función corre en el checkout y cada `Target` acepta un campo `quantity` que limita a cuántas unidades aplica cada descuento → así se arma la curva incremental. Confirmado en docs oficiales (`shopify.dev/docs/api/functions/latest/discount` y `.../product-discount`).
- ✅ **Dato positivo:** Shopify Functions vía **apps públicas** funcionan en **todos los planes** (no solo Plus). DiscountFlow es pública → sus clientes pueden usarla. (La restricción "solo Plus" aplica a *custom apps*.)
- **Requiere:** extensión Function (Rust o JS→Wasm) en `extensions/`, `shopify app deploy`, nuevo tipo de campaña `INCREMENTAL` en el enum `CampaignType`, migración Prisma aditiva y config vía metafield.
- **Competencia:** categoría validada pero saturada — Progressive Discount (VGroup) ~$11.99/mes; Dealeasy free–$24.99; Kite $19–49. La mayoría hace **volumen**, no incremental estricto.
- **Esfuerzo:** **L, bordeando XL** (skill nueva; el equipo no tiene experiencia con Functions).

**Recomendación:** orden sugerido = ambiente dev (✅ hecho) → sistema de **feature flags** → construir INCREMENTAL detrás de un flag → activar solo en la dev store → luego en Greta. Antes, verificar con el cliente si le sirve *volumen* (mucho más simple) en vez de *incremental estricto*.
